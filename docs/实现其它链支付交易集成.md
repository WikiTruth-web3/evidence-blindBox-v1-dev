# 外部链支付交易集成 (跨链/Zcash 支付方案)

## 1. 背景与目标

当前 Evidence Market 的底层设计不仅需要支持在 Oasis Sapphire 链上使用 ERC20 代币流转，还需要向用户提供**更高强度的资金隐私保护**，即支持外部隐私链（如 **Zcash**）进行支付。

由于外部链的资金流转无法直接被 Sapphire 合约感知，我们需要引入一套**执行者（Executor/Oracle）架构**：开发一套专门针对外部链的合约变体。这套合约不涉及 Sapphire 上的实际代币转移，仅用于状态机流转和账本记录，并由官方后端作为 Executor 桥梁进行状态同步。

---

## 2. 合约架构设计

为了实现高内聚低耦合，并且完美兼容未来的扩展，交易体系被拆分为一个**底层基础合约**和两个**上层变体合约**：

### 2.1 基础层 (Base)

- **`Exchange` 合约**（实现 `IExchange` 接口）：
  - **职责**：负责所有基础的交易变量数据维护、状态机流转逻辑（如上下架状态、修改盲盒价格/截止日期、退款仲裁逻辑、订单完成状态）。
  - **特点**：**绝对不包含任何支付/资金操作**。它只管“物”的归属权和状态，不管“钱”怎么流转。

### 2.2 支付执行层 (Implementations)

基于 `Exchange`，我们派生出两条平行处理“钱”的业务线：

1. **`Exchange` 合约**（实现 `IExchange` 接口）：

   - **核心职责**：处理 Sapphire 链上的原生/ERC20 代币购买操作。
   - **主要接口**：`buy(boxId)` 和 `bid(boxId)`。
   - **关联资金流**：对接现有的 `FundManager`，执行真实的链上 ERC20 扣款与分发。

2. **`BuyExecutor` 合约**（实现 `IBuyExecutor` 接口）：
   - **核心职责**：处理跨链（如 Zcash）的订单操作。
   - **主要接口**：`buyWithExecutor(...)` 和 `bidWithExecutor(...)`。
   - **关联资金流**：对接针对跨链账本的 `FundManagerOtherChain`，仅做纯数据的记账，不发生真实的链上资产转移。

---

## 3. 跨链版核心合约设计

### 3.1 BuyExecutor (跨链执行合约)

仅供官方白名单 Executor（执行账户）调用的交易接口：

- `buyWithExecutor(uint256 boxId, uint256 amount, string memory chainToken, string memory txHash)`

  - **权限**：仅限 `executor` 账户调用。
  - **逻辑**：由执行者证明链下已收到款项（记录对应的外部链和 txHash）。合约直接将 BlindBox 状态置为 `Paid`，记录买家 ID，并设置退款保护期。没有任何 ERC20 转移。

- `bidWithExecutor(uint256 boxId, uint256 amount, string memory chainToken, string memory txHash)`
  - **权限**：仅限 `executor` 账户调用。
  - **逻辑**：记录链下竞拍款项已收到，更新最高出价人和拍卖时间。

### 3.2 FundManagerOtherChain (跨链资金管理合约)

提供基于账本的虚拟资金记录：

- `recordOrderAmount(uint256 boxId, bytes32 userId, uint256 amount, string memory chainToken, string memory txHash)`

  - **权限**：仅限 `BuyExecutor` 或 `executor` 调用。
  - **逻辑**：在合约中记录该订单的外部资金流水，标记资金来源链（如 `Zcash-ZEC`）和交易哈希，用于不可篡改的账本存证。

- `allocationVirtualRewards(uint256 boxId)`
  - **逻辑**：当订单完成时（由 `Exchange` 触发），计算 Minter、Seller、DAO 等各方的虚拟收益比例并记账，通知后端准备在链下进行最终结算打款。

## 4. 完整业务流程

### 4.1 购买流程 (Buy / Bid)

1. **发起**：用户在前端点击购买，生成订单，并通过 Zcash 向官方账户打款。
2. **确认**：官方后端（Executor）监测 Zcash 节点，确认资金已在 Zcash 网络到账。
3. **上链执行**：Executor 调用 `BuyExecutor.buyWithExecutor(boxId, amount, "Zcash-ZEC", txHash)`。
4. **生效与记账**：
   - `BuyExecutor` 将盲盒状态改为 `Paid`。
   - 调用 `FundManagerOtherChain` 将该笔外部交易 Hash 上链存证。

### 4.2 订单完成与收益结算 (Complete Order)

1. **完成**：买家验证内容无误，调用 `Exchange.completeOrder`，盲盒状态变为 `Delaying`。
2. **记账**：底层触发 `FundManagerOtherChain` 划分收益份额，并抛出跨链结算事件。
3. **结算**：官方后端监听到结算事件后：
   - 获取 Minter 的收款偏好。
   - 如果是 Zcash，官方后端从资金池向 Minter 的 Zcash 地址打款。
   - 如果是链上代币，官方后端使用自有资金池向 Minter 在 Sapphire 链上的地址转账。

### 4.3 退款流程 (Refund)

1. **申请**：买家在保护期内发现内容虚假，调用 `Exchange.requestRefund`，状态变为 `Refunding`。
2. **仲裁/同意**：DAO/Minter 同意退款，发出退款许可。
3. **退款执行**：官方后端监听到退款许可后：
   - 后端从 Zcash 官方资金池将原资金原路退还给买家。
   - 退款完成后，后端可能调用合约接口更新退款核销状态，彻底完结该订单。

---

## 5. 安全与风险管理

由于该方案引入了中心化的 Executor 环节，必须注意以下风险：

1. **Executor 权限保护**：Executor 账户是连接链下资产与链上资产的唯一受信桥梁。必须使用多签（Multi-sig）或安全的 KMS 系统来保管私钥。
2. **重放与状态不一致**：后端的交易确认逻辑必须保证幂等性，防止 Zcash 的一笔 `txHash` 在 Sapphire 链上触发多次 `buyWithExecutor`。
3. **汇率波动容忍度**：外部代币到盲盒定价代币之间存在汇率波动。提交上链的 `amount` 应在前端报价时预留合理的滑点，由 Executor 判断金额是否足够完成订单。
